# 预览、证据与交付

## 预览产品

按用途保留少量清晰视角，例如建筑整体、正面、端面、室内总览、值机、安检、候机、到达和跨层交通。将调试坐标、历史问题专用镜头移出普通选择器。整体视角覆盖全部主体，近景确实能看见对象；按屏幕比例和控制面板占位适配。

楼层控制按真实高度裁切，避免把浮空设施误当作楼板错误。动线使用基于几何验证的路线、明确箭头和颜色；支持独立开关、组合显示、清除、定位。楼层切换不应偷偷清除选择。绘制在墙前的高亮线只是显示方式，不能当作没有穿墙的证据。

移动速度依据建筑尺度设置，提供调速和临时加速。用真实键盘事件测试 WASD、升降和加速：检查焦点、按钮/输入框干扰、丢焦清键、多键斜向归一化和低帧率。不能只检查速度常量；本次出现过按键开始结束均落在慢帧之间，导致移动为零。采用可靠的按键状态与时间积分，并合理限制恢复焦点后的时间步长。

检查模型和动线加载失败提示、GLB 下载、浏览器异常、窄屏溢出与可访问的控制标签。展示界面依用户偏好不放修订编号或冗余说明，必要来源署名保留，技术限制写入维护文档。

## 可维护目录

建议结构按规模精简，不能为目录形式创造空文件：

```text
index.html / app.js / style.css
assets/       模型、纹理、已验证的动线
source/       参数、空间台账、生成器
references/   来源与参考图
tests/        几何/连通性/浏览器检查与报告
archive/      确有历史资料时归档
```

不要复制几十套 GLB 当作修复记录。保留可重建源码和必要历史；清理时先检查引用和服务根目录。原位更新保留同一入口；移动源码之后调整资源路径并实际从整理后的路径构建验证。Windows 递归移动或删除前检查源/目标绝对路径均在任务目录内，使用同一套原生文件操作。

## 交付顺序

1. 构建到临时产物或源码输出位置，检查退出码及新文件哈希。
2. 对该文件验收并生成相应动线；只发布检查通过的匹配文件集合。
3. 将模型、动线同步到预览和下载位置。需要时使用临时文件加重命名，避免浏览器读到半写入资源。
4. 从正式入口重新加载验证，处理缓存。确认 UI 下载和已验收模型为相同字节。
5. 记录检查快照和截图。报告未覆盖范围，不声称未执行的检查通过。

## 验收清单格式

`scripts/verify_delivery.py` 只负责核对文件、哈希与记录关联，不替代任何实际检查。以下是结构示例，哈希必须从真实文件计算；只有检查确实执行且通过才写 `pass`。

```json
{
  "artifacts": {
    "model": {"path": "assets/building.glb", "sha256": "真实 SHA-256"},
    "routes": {"path": "assets/routes.json", "sha256": "真实 SHA-256"},
    "viewer": {"path": "app.js", "sha256": "真实 SHA-256"}
  },
  "required_checks": ["geometry", "circulation", "visual", "viewer"],
  "checks": [
    {
      "id": "geometry",
      "status": "pass",
      "scope": "本次修改涉及的楼板、墙和设备净空",
      "artifacts": {"model": "验收时的模型 SHA-256"},
      "evidence": [{"path": "tests/geometry.json", "sha256": "报告 SHA-256"}]
    }
  ]
}
```

所有路径相对清单所在目录，且必须留在目录内。为每个必需检查补全记录，示例只有一项，因此不能直接通过。`visual` 应绑定模型及实际截图；`viewer` 绑定模型、动线及页面相关文件。HTML/CSS、参考台账或生成源码需要一致性校验时分别加到 artifacts 并绑定到相关检查。

先依据任务要求确定 `required_checks`，不能为了通过检查删掉失败或尚未执行的项目。脚本验证范围仅为文件一致性，即使报告和截图哈希一致，内容也仍需要人工/模型检查。
